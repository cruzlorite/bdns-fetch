# Roadmap

Pending work, in rough priority order. Issues with the source API do not belong here; they live in [section 8 of bdns-api-behavior.en.md](bdns-api-behavior.en.md#8-known-api-issues).

- **Group H endpoints** (`organos_codigo`, `organos_codigoadmin`). Not implemented; the rest of the official catalog is covered.
- **Live verification of PostgreSQL and MySQL.** They are compatible by design (portable SQL), but the full SCD2 cycle is only verified against SQLite (tests) and BigQuery (live). A CI job with a Postgres service container would close the gap.
- **Validate records before versioning them.** A record missing its natural key, or carrying a null one, takes down the whole run with a `KeyError` during staging instead of being discarded the way `_skip_malformed` already handles HTML error pages. Same for the registration date on the entities that use it: absent, null, or carrying a time component (`2020-01-05T00:00:00`) blows up `strptime`. The fix is three per-record checks — key present, key not null, and registration date present, not null and parseable — that discard the row and record it in `_sync_errors`, reusing the table and the `context`/`content` pair that already exist; no schema change needed. With a ceiling, though: if discards exceed some share of the batch the run must fail, because silently discarding a whole batch leaves staging empty, and window-scoped deletion detection then closes the entire window as deletions. None of this has ever happened in production (two months of operation, zero missing or null keys, zero missing registration dates where they belong), so this is insurance, not an emergency. One side effect to keep in mind: runs that fail today would start succeeding with `rows_skipped > 0`, so the job-failure alert stops covering this case and that counter needs watching too.
- **Natural-key invariant.** Two rows sharing a `_natural_key` with different hashes mean the key is wrongly defined, but today the engine neither handles it nor detects it: it inserts two `_is_current` rows for the same key and, from then on, every run closes and reinserts them indefinitely, reporting changes that never happened at the source. The check is a `GROUP BY _natural_key HAVING COUNT(DISTINCT _row_hash) > 1` over staging before the diff, and it must fail the run rather than drop rows: a `failed` run naming the offending key is actionable information. Byte-identical duplicates, on the other hand, must stay tolerated: they are the pagination artifact [`data-caveats.en.md`](data-caveats.en.md) explains, and the insert's `DISTINCT` already handles them. Checked against the live target: zero duplicate keys across all 23 tables (~45M current rows), so switching it on breaks nothing already synced.
- **Payload redaction (drop or anonymize fields).** A `Sink` decorator (`RedactingSink(inner, drop=[...], anonymize={...})`) applied in the CLI wiring: it wraps any sink without touching it and syncers never know. It must act **before** `_row_hash` is computed — redacting after would turn changes in a dropped field into new versions with identical stored payloads. It must refuse to touch `key_fields` and `reg_date_field` (they would break the natural key and deletion detection). Strategies: drop, null out, or pseudonymize with salted HMAC (allows grouping by beneficiary without exposing the tax ID). The policy is passed via repeatable CLI flags and lives in the operator's scripts, like the cadence and the dates. Caveat: changing the policy later changes every hash, and the next sync re-versions the whole table; redaction is ideally decided before the full load.
- **File sink (Parquet).** A second implementation of the `Sink` interface, for non-SQL targets. The interface is already designed to allow it.

# Roadmap

Pending work, in rough priority order. Issues with the source API do not belong here; they live in [known API issues](explanation/bdns-api-behavior.md#api-issues).

- **Group H endpoints** (`organos_codigo`, `organos_codigoadmin`). Not implemented; the rest of the official catalog is covered.
- **~~Live verification of PostgreSQL.~~** Done: the full suite runs in CI against a PostgreSQL service container as well as SQLite. It surfaced that the bare `NULL` literal for `_valid_to` was rejected by PostgreSQL on every run.
- **~~Validate records before versioning them.~~** Done, with one correction: what this entry claimed was only true for an *absent* key. A *null* key took nothing down. It serialized to the literal key `[null]`, so every record missing that field landed on the same key and they overwrote each other run after run, under a `success` event. The sink now rejects per record: not a JSON object, key absent, key null, or a registration date absent, null, or not parseable as `%Y-%m-%d`. The row is dropped and recorded in `_sync_errors` with the reason. The ceiling is there too: the run fails if rejects leave the batch empty, or if they exceed 10% with at least five of them, so one broken record in a narrow window does not block the day. It covers all 23 entities, not just the three on the detail path. The side effect this entry warned about holds: runs that used to fail now finish with `rows_skipped > 0`, so that counter needs watching alongside the job-failure alert.
- **~~Live API contract check.~~** Done: `bdns-sync check-api`, which `delta_load.sh` runs once before the cadence. The tests can only pin *our model* of the API, not the API: `tests/fake_client.py` implements the same semantics, so a change upstream would leave CI green forever while production loses a day per chunk boundary. The probe asks the real service whether `fechaRegFin` is still exclusive and `fechaHasta` still inclusive, whether two adjacent days are disjoint and sum to the two-day range, and whether records still carry their natural key and registration date. It fails open on purpose: a transient error or an empty probe day is reported and exits zero, and it only aborts when the API returns valid data contradicting an invariant.
- **Natural-key invariant.** Two rows sharing a `_natural_key` with different hashes mean the key is wrongly defined, but today the engine neither handles it nor detects it: it inserts two `_is_current` rows for the same key and, from then on, every run closes and reinserts them indefinitely, reporting changes that never happened at the source. The check is a `GROUP BY _natural_key HAVING COUNT(DISTINCT _row_hash) > 1` over staging before the diff, and it must fail the run rather than drop rows: a `failed` run naming the offending key is actionable information. Byte-identical duplicates, on the other hand, must stay tolerated: they are the pagination artifact [the reading notes](explanation/data-caveats.md) explains, and the insert's `DISTINCT` already handles them. Checked against the live target: zero duplicate keys across all 23 tables (~45M current rows), so switching it on breaks nothing already synced.
- **Payload redaction (drop or anonymize fields).** A `Sink` decorator (`RedactingSink(inner, drop=[...], anonymize={...})`) applied in the CLI wiring: it wraps any sink without touching it and syncers never know. It must act **before** `_row_hash` is computed — redacting after would turn changes in a dropped field into new versions with identical stored payloads. It must refuse to touch `key_fields` and `reg_date_field` (they would break the natural key and deletion detection). Strategies: drop, null out, or pseudonymize with salted HMAC (allows grouping by beneficiary without exposing the tax ID). The policy is passed via repeatable CLI flags and lives in the operator's scripts, like the cadence and the dates. Caveat: changing the policy later changes every hash, and the next sync re-versions the whole table; redaction is ideally decided before the full load.
- **File sink (Parquet).** A second implementation of the `Sink` interface, for non-SQL targets. The interface is already designed to allow it.
